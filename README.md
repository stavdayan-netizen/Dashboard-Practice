# Dashboard Practice

A single-page **Tenant Maintenance Dashboard** demo for a property manager, built per [SPEC.MD](SPEC.MD). Plain HTML/CSS/JS, no build step, no backend, no API keys. Sample data only — it does not connect to Zillow, TurboTenant, tenants, or any AI model.

## Stack

- `index.html`, `styles.css`, `app.js` — the app (vanilla JS, no framework/build tool).
- [PapaParse](https://www.papaparse.com/) (CDN) — proper CSV parsing.
- [Chart.js](https://www.chartjs.org/) (CDN) — the donut and bar charts.
- `maintenance_requests.csv` — the 40-row sample dataset (source of truth).
- `data.js` — an embedded copy of the CSV, auto-generated by `generate-data.ps1`, used as a fallback so the app also works when you open `index.html` directly instead of through a server.

## Running it

**Option A — open directly (simplest):** double-click `index.html`. It works out of the box because the app falls back to the embedded copy of the data in `data.js`.

**Option B — local server (recommended if you have one handy):** serve this folder with any static server (e.g. VS Code's "Live Server" extension) and open it in the browser. This lets the app load `maintenance_requests.csv` straight from disk. No Node or Python? `serve.ps1` is a small built-in PowerShell static server:
```powershell
powershell -ExecutionPolicy Bypass -File serve.ps1
```
then open `http://localhost:8531`.

## Updating the demo data

`maintenance_requests.csv` is the source of truth. To change it:

1. Edit `maintenance_requests.csv`.
2. If you're serving the folder through a local web server, just refresh the page.
3. If you're opening `index.html` directly (file://), also regenerate `data.js` first:
   ```powershell
   powershell -ExecutionPolicy Bypass -File generate-data.ps1
   ```
   then refresh the page.

The dashboard's "as-of" date is **today's date** on the viewer's clock (`AS_OF_DATE`, near the top of `app.js`), and it moves on by itself at midnight. Rows dated after today are rejected, "Resolved This Month" counts the current calendar month, and year to date runs from January 1 of the current year to today. The sample data is dated through September 23, 2026, so as time passes the month KPI shows 0 until newer tickets are resolved, and a new year starts with empty year-to-date costs.

## Upload CSV / + New Request

Two header buttons let you try the dashboard with your own data, in-browser, without editing any files:

- **Upload CSV** replaces the dashboard's dataset with a CSV you pick from your computer (same 13-column format as `maintenance_requests.csv` — see the header row for the exact column order). `demo_upload_sample.csv` (linked via **Download demo CSV**) is a 36-row file you can download and re-upload to see it in action.
- **+ New Request** opens a form to add one request by hand (its ID is generated automatically).

Both go through the same validation as the built-in loader, and both only change data in memory for the current browser tab — nothing is written back to `maintenance_requests.csv`. Reload the page to return to the live/default data source.

## Airtable connection

The dashboard's primary data source is a live Airtable base ("Property Maintenance Tickets" → "Maintenance Tickets" table), so anyone who opens the deployed page sees data coming from a real database, not a static file. This is wired up in `app.js`:

```js
const AIRTABLE_CONFIG = {
  baseId: "appIl5LOY1FMfCPUR",
  tableId: "tblk60sOTkEpyDmr1",
  token: "..." // a real Airtable Personal Access Token
};
```

**Why it's safe for this token to be public source code:** it's a Personal Access Token scoped to exactly one permission (`data.records:read`) on exactly one base. It cannot write, delete, or reach any other base or workspace — the worst case if someone else finds it is that they can also read this one table of fictional maintenance requests. Never put a token with write access or multi-base access here.

**What happens without a valid token:** `init()` in `app.js` tries Airtable first; if the request fails for any reason (bad/missing token, network issue, rate limit), it silently falls back to the bundled `maintenance_requests.csv` (or the embedded `data.js` copy). A small badge next to the page title ("Live: Airtable" / "Sample data (CSV)") always shows which one is actually active.

**Automatic refresh (once an hour):** an open page re-reads Airtable and the weather every hour, and also when you come back to the tab after being away that long. It redraws quietly: your Property filter, selected tab and open dialogs stay as they are. If a refresh fails, the data already on screen stays. Data from an uploaded CSV is never replaced, and requests added with + New Request are kept. Nothing refreshes more often than that, so reload the page to see an Airtable change right away.

**Regenerating the token:** if you ever need a fresh one, create it at [airtable.com/create/tokens](https://airtable.com/create/tokens) scoped the same way (one base, `data.records:read` only), then replace the `token` value in `AIRTABLE_CONFIG`.

## Vendor Research

The **Vendor Research** header button opens a second screen that lists only open tickets. The ticket details dialog (click any row) also has a **Vendor Research** button for New and In Progress tickets, which opens this screen with that ticket already selected. Select a ticket to see its issue and full address (from the Airtable `Full Address` lookup), then click **Find Vendors**. Only then does the app:

1. Derive a short search term from the ticket's issue and category (`deriveVendorSearchTerm()` in `app.js`, e.g. "Furnace not producing heat" → "furnace repair").
2. Run Apify's Google Maps Scraper (`compass/crawler-google-places`) for "`<term> near <full address>`" and show up to 5 vendors with name, category, rating, review count, phone, website, and a Google Maps link.

The Apify token must never reach the browser, so this screen only works through the local server, which keeps it in `.env`:

1. Copy `.env.example` to `.env` and set `APIFY_TOKEN=` to your Apify API token (`.env` is gitignored).
2. Run `powershell -ExecutionPolicy Bypass -File serve.ps1` and open `http://localhost:8531`.

On the public GitHub Pages site (or a page opened as a file) the screen still opens, but shows a notice and the button stays disabled.

Notes:
- Each search starts one Apify run, about $0.03 (start fee plus 5 places), capped at $0.50 per run. A run usually takes 15–60 seconds.
- The address goes into the Google Maps search text instead of the actor's `locationQuery` field, because that field can't geocode street addresses.
- `serve.ps1` refuses to serve dotfiles such as `.env`, only accepts searches from the page it serves, and exposes `/api/status`, `/api/vendors/search` and `/api/vendors/result` on localhost only.

## Weather & Property Alerts

Between the KPI cards and the charts, a **Weather & Property Alerts** section shows one compact card per property (just the selected property when the Property filter is set). On desktop all four cards sit side by side in one row; they drop to two columns on tablets and one on phones. Each card has:

- a sky image that matches the current condition (clear, partly cloudy, cloudy, fog, drizzle, rain, snow, thunderstorm, day or night) with the temperature and condition written over it, plus wind and chance of rain;
- a borderless 7-day strip (day, small icon, high/low) with a dot under any day that has an alert;
- maintenance alerts for the next 7 days: today's alerts in a highlighted panel, later days as one short line each. A card with alerts today gets a red (high risk) or orange (moderate) ring.

The sky images are generated in the browser (canvas), so there are no image files, downloads or licensing to worry about.

How it works (all in `app.js`, no API keys, and it works on the public GitHub Pages site too):

1. The property's full address (the Airtable `Full Address` lookup) is located with the **US Census Geocoder**. It sends no CORS headers, so the page uses its JSONP mode. Exact matches are cached in the browser's `localStorage`. If the Census has no match, the card falls back to the address's ZIP area and says the location is approximate.
2. The 7-day forecast comes from **Open-Meteo** (free for non-commercial use, up to 10,000 calls a day; attribution to Open-Meteo is shown under the cards). Forecasts are kept in memory for 15 minutes, so changing the Property filter doesn't refetch.
3. Alerts are simple rules over the daily forecast, not official warnings:

| Alert | Moderate risk | High risk |
| --- | --- | --- |
| Freezing temperatures / hard freeze | low at or below 32°F | low at or below 20°F |
| Heavy rain | 1 in or more in a day | 2 in or more |
| Snow | 1 in or more | 4 in or more |
| Strong winds | gusts of 40 mph or more | 58 mph or more |
| Extreme heat | high of 90°F or more | 100°F or more |

The thresholds live in `alertsForDay()` in `app.js`. The section needs each property's full address, so it shows a short notice instead of cards when the data comes from the sample CSV or an uploaded CSV (those rows have no address).

## Demo mode (`?demo=1`)

Add `?demo=1` to the dashboard address (for example `http://localhost:8531/?demo=1`) to see a fully fictional demo for **10 Harbor View**. It reads the files in `demo/` instead of Airtable: 25 fictional tickets, the property's address (so the weather section works), and a badge and note saying the data is fictional. Nothing is read from or written to Airtable, the real data is untouched, and without `?demo=1` the dashboard behaves exactly as before. Like Vendor Research, it needs a web server, not a file opened directly.

The `demo/` folder also holds fictional equipment, equipment history, utilities and shutoff records for the upcoming Systems & Equipment views and the AI Maintenance Agent tests. They are not shown in the dashboard yet. See `demo/README.md` for the data structure, the allowed values and how each file maps to a future Airtable table.

## Tenant Maintenance Portal (`tenant.html`)

A separate, phone-friendly page where a tenant reports a problem. It is not linked from the dashboard and the dashboard code is unchanged. It is published with the rest of the project on GitHub Pages at **https://stavdayan-netizen.github.io/Dashboard-Practice/tenant.html** (every push to `master` updates it), and also works from a local server (`http://localhost:8531/tenant.html`).

**Admin settings are hidden from tenants.** The page shows only the form. The webhook URL field lives in an **Admin settings** panel that stays closed until you press the small "Admin settings" link at the very bottom of the page (press it again to hide the panel). A tenant who submits on a device without a saved URL just sees "This form isn't ready yet. Please contact your property manager." Error messages are plain for tenants; while the admin panel is open they also include technical detail (such as the HTTP code), and the same detail is always written to the browser console.

The form asks for three things: **Property** (the live list from the Airtable Properties table), **what's the problem**, and **priority** (Low, Medium, High, Urgent). On submit the page POSTs the request to a **Make custom webhook**, and a Make scenario creates the ticket in the Airtable Maintenance Tickets table. A success or error message appears under the title.

Files: `tenant.html`, `tenant.css`, `tenant.js`. To fill the property list, `tenant.js` reads the dashboard's read-only Airtable settings out of `app.js`, so the token still lives in one place.

### What the page sends

A form post (`application/x-www-form-urlencoded`) with these fields, named like the Airtable Tickets fields:

| Field | Value | Airtable field |
| --- | --- | --- |
| `id` | Generated, like `TP-20261015-K3F9` (the same ID is reused if you retry a failed send) | `id` |
| `date_created` | Today's date, `YYYY-MM-DD` | `date_created` |
| `property` | The property's Airtable **record ID** (`rec…`) | `property` (linked record) |
| `property_name` | The property's name. Only for readability in Make; there is no Airtable field for it | none |
| `issue` | The description the tenant typed | `issue` |
| `category` | Guessed from keywords in the description (for example "leak" gives Plumbing); `General` if nothing matches | `category` |
| `priority` | `Low`, `Medium`, `High` or `Urgent` | `priority` |
| `status` | Always `New` | `status` |

`tenant`, `assigned_to`, `date_resolved`, `cost`, `cost_date` and `ai_summary` are not sent. The category is sent because the dashboard rejects a ticket without one; the manager can change it in Airtable.

### Setup

The scenario **"Tenant Portal request → Airtable ticket"** has already been built in Make (team "My Team", left switched off). It uses the same three modules as step 1 below, with the Airtable fields mapped by field ID, so steps 1 and 2 only need repeating if you rebuild it. The webhook URL is shown in the scenario's webhook module in Make, and goes in the portal's Admin settings (step 3), never in this repo.

1. **Make: create the scenario.** New scenario, then add these modules in order:
   1. **Webhooks → Custom webhook.** Create a webhook and copy its URL.
   2. **Airtable → Create a record** on the base's **Maintenance Tickets** table. Map each field from the table above: `id`, `date_created`, `issue`, `category`, `priority`, `status`. For the linked `property` field, add one item and map `property` to it (Airtable wants the record ID, which is what the page sends).
   3. **Webhooks → Webhook response** (so the page can confirm the send). Status `200`, body `Accepted`, and a custom header `Access-Control-Allow-Origin` with the value `*`. Without this header the ticket is still created, but the browser blocks the reply and the page can only say it couldn't confirm delivery.
2. **Teach Make the fields.** Click **Run once** on the scenario, then submit one request from the portal (see Testing). Make learns the field names from that first request. Then turn the scenario **On**.
3. **Tell the page the URL.** Open `tenant.html`, press **Admin settings** at the bottom of the page, paste the webhook URL and press **Save** (then press **Hide admin settings**). It is stored only in that browser's `localStorage` (key `dashboardPractice.tenantWebhook.v1`), never in the code or the repo. Each device or browser needs this once, so a tenant's own phone will not have it unless you give them the URL.

### Testing

1. Put the scenario in **Run once** (or leave it On) and open `tenant.html` with the URL saved.
2. Pick a property, describe a problem such as "Kitchen sink is leaking", pick a priority, and press **Submit request**. You should see "Request sent" with a reference like `TP-…`.
3. In Make, open the scenario's execution history: the webhook module should show the fields above and the Airtable module should have created a record.
4. In Airtable, find the new row (`id` matches the reference), with status `New` and the right property.
5. Error checks: submit with nothing filled in (inline errors appear); submit with no URL saved (tenants see "This form isn't ready yet"; with Admin settings open the message also says the URL is missing); save a URL that isn't `https://` (rejected); turn the scenario off and submit (a plain error, plus the HTTP code while Admin settings is open).

### Things to know

- **The dashboard's "today" matches the portal's.** Both use the viewer's local date, so a ticket created today is accepted by the dashboard. If a device's clock is set to an earlier date than the ticket's, the dashboard rejects that ticket until the clocks agree.
- **The webhook URL is a secret.** Anyone who has it can create tickets, so share it only with people you want submitting. Because it is saved per browser, a real tenant would have to be given it, which is fine for a class demo but not for a public rollout. A real rollout would put a small server in between.
- Nothing from the portal is stored by the page itself; the only thing kept in the browser is the webhook URL.
